# Правила роботи агентів у цьому проєкті

## Делегування змін

- Кожну окрему правку або незалежний блок змін спочатку передавати окремому субагенту.
- Не об’єднувати в одного субагента непов’язані правки лише заради економії викликів.
- Основний агент відповідає за декомпозицію, уникнення конфліктів між файлами, інтеграцію, збірку та фінальну перевірку.
- Якщо паралельні слоти зайняті, повторно використовувати завершеного агента через окреме follow-up завдання.

## Вибір моделі за складністю

- **Мала механічна правка** — `gpt-5.6-luna`, reasoning `low` або `medium`.
  Приклади: локальна заміна розмітки, простий CSS-fix, перейменування, вузька перевірка.
- **Звичайна продуктова правка** — `gpt-5.6-terra`, reasoning `medium` або `high`.
  Приклади: компонент, адаптив одного архетипу, форма, кілька пов’язаних станів.
- **Складна або ризикована правка** — `gpt-5.6-sol`, reasoning `high` або `xhigh`.
  Приклади: інформаційна архітектура, навігаційна система, великий рефакторинг, зміни кількох архетипів, критична інтеграція.

Перед створенням агента явно зафіксувати складність і вибрану модель у його завданні. Для model override використовувати обмежений fork-контекст, а не full-history fork.

## UI та UX

- Для кожної frontend-правки застосовувати доступні дизайн-скіли, зокрема `impeccable` і `design-taste-frontend`, якщо вони відповідають задачі.
- Не використовувати Playwright і не виконувати автоматичний screenshot/browser-pass.
- Візуальну перевірку на mobile і desktop виконує користувач; агенти виконують лише статичні, структурні та CSS-перевірки.
